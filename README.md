# Relay CRM

Relay CRM is a shared team inbox and customer workspace for WhatsApp Business. The current messaging integration uses Twilio WhatsApp senders across one workspace, so teams can answer customers, route conversations, and keep a single customer history across numbers. The product requirements are in [`whatsapp-crm-prd.md`](./whatsapp-crm-prd.md).

What works today:

- **Inbox:** shared and team inboxes with assignment, tags, internal notes, saved views, canned replies, Twilio text replies in the 24-hour window, and approved Twilio Content templates outside it.
- **Numbers and routing:** multiple Twilio accounts and approved sender numbers, segment/team/country-prefix routing, and guarded backup-number routing.
- **Customers:** contact directory, CSV import, duplicate merge, consent history, export, legal hold and retention-based deletion.
- **Security and operations:** team invitations, roles, MFA, session management, audit history, webhook recovery, malware scanning for attachments, in-app and email alerts, and reports.

Still open before production: complete Twilio account and sender configuration, public webhook URL verification, scheduled jobs for webhook recovery, retention cleanup and alert emails, and live failover verification. Without `DATABASE_URL` the app runs in a single-process local demo mode; messages typed there are not sent.

## Stack

- Next.js App Router
- TypeScript and React
- Tailwind CSS v4
- **shadcn/ui is the required UI component system** (`components.json` is configured; reusable primitives live under `src/components/ui`)
- PostgreSQL schema, versioned SQL migrations, and relational repository; local JSON remains available when no `DATABASE_URL` is configured
- Lucide icons

## Start locally

```bash
npm install
npm run dev
```

Open `http://localhost:3000`.

The app uses a local JSON file under `data/` when `DATABASE_URL` is unset, and PostgreSQL when it is configured. Local JSON mode is a demo only; inbox messages typed there are not sent. In PostgreSQL mode, sender numbers marked `TWILIO` send free-form text during an open customer service window and approved Twilio Content templates through Twilio's Messages API outside it. The inbox fetches templates from Twilio for the selected sender account and the send API checks current WhatsApp approval status before dispatch. Twilio delivery callbacks update message status and provider error details. Set `APP_BASE_URL` to the public HTTPS app URL in a deployed environment so Twilio can reach `/api/webhooks/twilio` and `/api/webhooks/twilio/status`. In PostgreSQL mode, initial owner setup verifies mailbox control through a one-time link before activating the account; production also requires a separate `OWNER_SETUP_SECRET` known to the operator. Admin setup/login, verified team invitations, team and sender-number management, saved customer segments, deterministic segment/team/country-prefix routing rules, webhook and media recovery, login throttling, password recovery, password changes, revocable sign-in sessions, current-role session validation, authenticator MFA, guarded automatic failover, and Twilio multi-account configuration are implemented. Admin-assisted MFA recovery revokes active sessions, audits the recovery, and attempts a security notice to the affected member using the configured Resend email settings. Provider account setup and scheduled recovery setup remain deployment work.

In PostgreSQL mode, inbox access is enforced by the server: agents see their assigned conversations and the unassigned queue; supervisors see their own conversations, the unassigned queue, and conversations assigned to their teams; owners and admins can see all workspace conversations. Message sends, conversation changes, internal notes, consent edits, and attachment reads recheck the caller’s access. New contacts are assigned to the creating user so they remain visible when the workspace has assignment-based access enabled. Local JSON mode is a single-process development setup and does not model team membership scopes.

## PostgreSQL

The intended production data store is PostgreSQL. The schema is in `prisma/schema.prisma`, and `.env.example` shows the expected `DATABASE_URL`. Versioned SQL migrations live under `prisma/migrations/` and the migration runner applies them in order, including the current team, contact-merge, canned-reply, saved-view, template-lifecycle and outbound retry-claim migrations. Importing local data is opt-in: with `CRM_IMPORT_LOCAL_DATA=true`, the first application access to an empty workspace imports an existing `data/crm-store.json` once and records it in `LocalDataImport`. The built-in demo customers and numbers are never imported; a demo number still used by a real local conversation is kept for history but imported as paused. If the database already contains workspace records, it remains authoritative and the local file is not merged.

The checked-in migration runner uses the `pg` driver and applies SQL files transactionally with a SHA-256 checksum ledger and an advisory lock. Name new migrations `YYYYMMDDHHMMSS_description` with the current UTC time; the runner refuses a pending migration that sorts before one already applied. Migration folders were renamed from future dates to `20261020…`; existing databases have their ledger entries carried over automatically. Copy `.env.example` to `.env.local`, update the database credentials, and run `npm run db:migrate` to create the PostgreSQL schema. Saved customer segments filter by tag, source, owner, and current WhatsApp consent. Admins can attach a saved segment to a routing rule; segment membership is evaluated from current contact fields for both sender selection and eligible failover candidates. Creating or deleting segments that can affect routing requires an MFA-verified admin session. Segment-specific rules precede country-prefix/team rules, then rule priority applies. A segment used by a routing rule cannot be deleted until that rule is updated. Failover events retain Meta error code, subcode, HTTP status, and the selected routing-rule ID/version for admin review. Login throttling stores only a hash of the normalized email and client IP, blocks after five failed attempts for 15 minutes, and prunes old rate-limit keys opportunistically. Configure the trusted reverse proxy to set `X-Real-IP` or append the client address to `X-Forwarded-For`; without PostgreSQL, the fallback throttle and session records are process-local and intended only for local development. Signed-in users can review and revoke active sessions from the account menu. In PostgreSQL mode, session records store a truncated IP and browser user-agent string; session creation and revocation actions are audited.

Every mutating `/api/*` request is checked against the browser `Origin` and `Sec-Fetch-Site` headers. Requests from another origin are rejected. Behind a reverse proxy, configure it to overwrite `X-Forwarded-Host` and `X-Forwarded-Proto` with the public request host and protocol; do not trust client-supplied forwarded headers. The Meta webhook is exempt from the browser-origin check because its raw body is authenticated with Meta's HMAC signature; scheduled server-to-server recovery endpoints continue to authenticate with their configured bearer secrets. Requests without browser-origin headers are allowed for server integrations.

Password reset and team invitations use Resend for transactional email. Set `APP_BASE_URL`, `RESEND_API_KEY`, and `PASSWORD_RESET_FROM` in the server environment, then run `npm run db:migrate`. Team invitations are workspace-scoped, hashed at rest, single-use, expire after 48 hours, and let the invited person set their own password after opening the emailed link. A new invitation to the same address revokes its earlier pending link. Invitation creation and acceptance are audited. The forgot-password response is generic; the same email and one-time link shape is sent whether or not the address belongs to an active account. Reset tokens are hashed in PostgreSQL, expire after 30 minutes, are single-use, and successful recovery revokes all active sessions. Requests are throttled per hashed email and IP. Configure a verified sender domain with Resend before enabling these flows in production. The mailer uses Resend's [Send Email API](https://resend.com/docs/api-reference/emails/send-email).

Authenticator MFA uses TOTP-compatible apps and one-time recovery codes. Enroll from Account security; the authenticator seed is encrypted using a key derived from `SESSION_SECRET`, and only hashes of recovery codes are stored. An authenticated user can replace an enrolled authenticator after verifying the current factor or an unused recovery code; the old authenticator remains active until the new one is confirmed, which rotates the recovery codes and records an audit event. If a user has lost both, an MFA-enrolled administrator can record a separate identity check and reset an agent/supervisor factor; only the workspace owner can recover an admin/owner account. Recovery revokes the target’s sessions, audits the reason and actor, and requires new MFA enrollment before that user can make protected administrator changes. When Resend is configured, the affected user receives a security email; delivery outcome is audited and the admin is prompted to notify them through a trusted channel if email could not be confirmed. Admin/owner sign-in requires the MFA challenge after enrollment. Completing MFA enrollment or replacement verifies the current session and revokes other active sessions; protected admin changes also require an MFA-verified session, so a session created before enrollment cannot inherit access. Store `SESSION_SECRET` as a long random secret and back it up securely; changing it makes enrolled authenticator secrets unreadable. Enroll every production administrator before onboarding live numbers.

Owner/admins can configure critical and warning email recipients in Admin → Alerts. This reuses the Resend API key and verified sender used by password recovery. Set a random `ALERT_EMAIL_SECRET` and schedule POST requests to `/api/admin/alerts/deliver` every few minutes. Email notifications are queued in the alert table and retried up to five times with stable Resend idempotency keys. Delivery is disabled by default. Admin inbox polling creates deduplicated warnings when a connected Meta authorization is within seven days of expiry and critical alerts once expired; reconnecting the WABA clears the old expiry alert. The alert contains no token value. In-app and email alerts for a specific WhatsApp business account or sender number open the WhatsApp numbers page focused on the affected record. The provider supports idempotency keys for email requests ([Resend documentation](https://resend.com/changelog/idempotency-keys)).

Customer exports are restricted to owners/admins and audited. PostgreSQL exports include profile fields, identifiers, consent evidence, conversations by sender number, message lifecycle and provider IDs, notes, attachment metadata, and redacted contact audit history. The standard JSON export excludes file contents. The **With files** export downloads a ZIP containing that JSON and clean, archived attachment files, mapped to their messages; unavailable or unscanned files are identified in the manifest. It is capped at 50 MB of attachment bytes, 25 MB for the manifest, and 500 files per export. Exported archives are generated in memory and delivered with private, no-store headers. Admins with an MFA-verified session can place contacts on legal hold or permanently delete a contact and its conversations from Customers. Deletion removes stored conversations and attachments, redacts matching webhook payloads and linked audit details, and records a minimal deletion event. Admins with MFA can also purge an individual stored file from the inbox while retaining its message and metadata; file access and purge actions are audited. Privacy controls require PostgreSQL. In Admin → Privacy, MFA-verified admins can configure automatic deletion for records whose conversations are all resolved and have had no activity for the selected number of days (30–3,650); 0 disables it. Contacts on legal hold are skipped. Configure a daily external POST to `/api/admin/retention` with a random `RETENTION_CLEANUP_SECRET` bearer token; each removal is transactional and audited. Matching webhook payloads are redacted before deletion. Backups and any external exports are outside the application’s deletion scope and must follow your organization’s retention process.

Admins can import customers from CSV under Customers → Import CSV. The importer previews name/phone/email validation and matches against primary and historical phone identifiers before selecting new records. Imports support up to 500 rows per 1 MB file and are audited in PostgreSQL. Include `consent`, `consent_source`, and `consent_wording_version` columns to import explicit WhatsApp opt-in or opt-out evidence; rows with unknown consent remain blocked from outbound messaging.

Consent records are append-only in PostgreSQL and include workspace, contact, channel, scope, status, evidence, timestamp, and optional recording user. The local JSON adapter stores the same consent history in an append-only array. Both the local message action and the live sender suppress contacts without recorded opt-in; the live sender also checks the customer-service window before dispatch.

### Meta Cloud API connection

For Meta Embedded Signup, configure `META_APP_ID`, `META_APP_SECRET`, and `META_EMBEDDED_SIGNUP_CONFIG_ID` alongside PostgreSQL and a long `SESSION_SECRET`. Create/configure Facebook Login for Business and the WhatsApp Embedded Signup flow in Meta, allow the app’s deployed domain, and complete Meta App Review and the permissions required for your provider setup. The exact access and partner requirements depend on whether you are onboarding your own business assets or acting as a Meta Tech Provider; Meta restricts Embedded Signup to eligible partner/provider setups ([Meta Embedded Signup guide](https://www.postman.com/meta/whatsapp-business-platform/documentation/du6gzjv/embedded-signup)). The Admin → WhatsApp numbers page launches the official flow, exchanges its authorization code on the server, validates the returned WABA, imports its phone numbers, subscribes the app to WABA webhooks, and stores the connection token encrypted using a key derived from `SESSION_SECRET`. Imported numbers start pending; PostgreSQL-backed approval and reactivation require a fresh Meta asset-list check that confirms the configured phone number ID is in the connected WABA and matches the CRM number. The latest safe check result and timestamp remain visible after reload in Admin → WhatsApp numbers; audit details omit the raw phone number and access token. This read-only check does not verify webhook delivery or prove that Meta will accept a message. Keep `META_APP_SECRET` and `SESSION_SECRET` in a managed secret store. If you already have a system-user token, `META_ACCESS_TOKEN` remains an optional fallback for WABAs not connected through signup; manual mapping is intended only for numbers already onboarded in Meta. This flow does not implement every partner provisioning step, such as partner system-user setup or any required credit-line configuration, and does not replace verification in WhatsApp Manager.

The webhook callback is `/api/webhooks/whatsapp`; in the Meta app Webhooks configuration subscribe to `messages`, `account_update`, `phone_number_quality_update`, `message_template_status_update`, and `message_template_quality_update`, then subscribe each connected WABA to the app. Use `META_WEBHOOK_VERIFY_TOKEN` for callback verification. The template status and quality fields require the applicable WhatsApp Business Management permissions; Embedded Signup does not replace app-level webhook-field configuration. The endpoint validates `X-Hub-Signature-256` against the raw request body, persists each event to `WebhookEvent.rawPayload`, and acknowledges it before processing. The admin Webhook health page processes persisted events, deduplicates inbound Meta message IDs, updates the shared contact/conversation timeline, and records delivery status changes. It retries persisted `RECEIVED`, `FAILED`, and stale `PROCESSING` events with bounded backoff and a 12-attempt limit. The same recovery action archives due inbound attachments, retries failed media downloads, and scans newly archived or previously stored encrypted media. Configure `CLAMAV_HOST` and `CLAMAV_PORT` to a private-network ClamAV daemon; inbound files are not available to agents until the scanner returns clean, and outbound attachments are blocked unless the scanner confirms they are clean. Scanner outages leave inbound media unavailable for retry and reject outbound uploads; detections are quarantined, removed from inbound storage, and raise a critical admin alert. It supports administrator initiated recovery and manual retry of the latest failed event. Uncorrelated status callbacks remain retryable until the corresponding outbound message is saved or the retry limit is reached. Its incident timeline includes alerts, failed webhook summaries, failovers, and administrative action names. Admins can download a JSON diagnostics bundle with aggregate health, masked sender numbers, and operational metadata; the bundle omits customer message content, raw webhook payloads, credential values, and raw provider error text. For scheduled recovery, configure an external scheduler to call `POST /api/admin/webhooks` with `Authorization: Bearer $WEBHOOK_RECOVERY_SECRET`; recovery is not run by an in-process timer.

The live sender supports free-form text and media inside the active 24-hour customer service window and approved templates outside it. The composer currently accepts JPEG/PNG images (5 MB), MP4 video and supported WhatsApp audio types (16 MB), plus PDF/text/Office documents (25 MB). Outbound attachments are encrypted and saved in PostgreSQL before dispatch; inbound WhatsApp media is fetched after webhook acknowledgement and saved encrypted in PostgreSQL, with checksums and bounded retries (25 MB inbound archive limit). The authenticated CRM media route serves stored files through signed, workspace- and user-bound URLs that expire with the active CRM session; it only renders a strict allowlist of image, audio, and video MIME types inline, and sends other files as downloads. Set and back up a stable `SESSION_SECRET` of at least 32 characters: it derives the encryption key for Meta credentials and archived media, so changing it without a planned re-encryption will make those records unreadable. Database backups contain encrypted attachment bytes and must follow your retention policy. Configure a live ClamAV service and consider external object storage for larger deployments. Admin-controlled attachment purge and media-inclusive customer exports are implemented. Meta documents media upload, retrieval, and supported file types in its [WhatsApp Cloud API media collection](https://www.postman.com/meta/whatsapp-business-platform/folder/13382743-ecb27be5-4d27-4763-bbee-6a8002c04bf3).

Template sync is available under Admin → Templates for WABAs associated with a CRM number. When the Meta app subscribes to `message_template_status_update` and `message_template_quality_update`, lifecycle changes, rejection reasons, and quality scores are persisted from signed webhooks, surfaced in the admin template list, and risky transitions create administrator alerts. The template list refreshes every 30 seconds; sync remains available for reconciliation. The current template sender supports numbered and lowercase named text variables in the BODY component; it excludes header/button variables and media templates. Text and media sending require the latest recorded WhatsApp opt-in and use the selected active number. Sending an approved template on a different active number creates/uses that number's conversation while preserving the shared contact history. Admins can enable guarded failover under Admin → WhatsApp numbers; it is off by default, limited to one retry for error code `133010`, and considers only active numbers in the same WABA. Confirm this code's sender-number scope against the actual Meta response in your deployment before enabling automatic switching in production. Admins can set the retry cap to zero or one, select a 0–120 minute customer-specific backup cooldown, and require administrator approval. Approved requests appear in Admin → Webhook health; approving sends one new copy through the backup after rechecking consent, template approval, team access, routing and (for free-form text) the service window. Failover records preserve the selected routing-rule ID and version; events using global sender priority are identified as default-priority decisions. The original failed message remains in its original number-specific thread. Approval actions require enrolled MFA, recheck that the backup still has a current Meta authorization, and an interrupted approval can be resumed with a stable idempotency key after the recovery wait. A free-text retry also requires an open service window on the alternate number. The affected sender is marked disconnected and the event is audited. An admin may separately choose an approved Utility template with one numbered or named BODY variable to send the new number to the customer after a successful retry; this is also off by default and requires recorded opt-in. Account-level restrictions, quality warnings, recipient/template errors, and uncertain outcomes never trigger failover. A timed-out request is marked `UNKNOWN`; check webhook status before retrying. WABA-level banned/restricted/disabled updates mark all mapped numbers Restricted; phone-quality updates are recorded for admins and do not trigger number rotation. Keep the app secret, access token, verification token, database, and raw webhook payloads private. For Meta's current API details, see [Meta's WhatsApp Cloud API message endpoint collection](https://www.postman.com/meta/whatsapp-business-platform/folder/13382743-ba8d099d-007e-4b52-b9f2-3cf3c60e4fbc), [webhook payload reference](https://www.postman.com/meta/whatsapp-business-platform/folder/tduohwq/webhook-payload-reference), and [status reference](https://www.postman.com/meta/whatsapp-business-platform/folder/fuaee8l/statuses-object). Meta describes the 24-hour support window as a rolling period refreshed by a user-initiated message; outside it, messages must use templates ([status reference](https://www.postman.com/meta/whatsapp-business-platform/folder/fuaee8l/status-reference)).

## Delivery failure classification

Provider-rejected messages retain a `failureClass` in PostgreSQL and the inbox shows it on failed outbound messages. The classifier recognizes the sender-registration error used by guarded failover, authentication/configuration HTTP failures, rate-limit responses, and unknown outcomes. Other provider codes remain `UNKNOWN_HOLD`; these classifications are descriptive and do not trigger automatic retries. An outbound timeout is saved as `UNKNOWN`, and HTTP 5xx responses are classified as `OUTCOME_UNKNOWN`; reconcile delivery status before creating another send. App-side idempotency does not guarantee provider-side deduplication. Webhook and media processing use bounded backoff, but outbound network/server errors are not automatically resent until provider semantics establish a definitive non-acceptance. WABA account restriction webhooks separately mark mapped numbers restricted and alert administrators. Extend the code map only after validating a code against the current Meta response behavior.
Owner/Admin users with MFA can create one audited retry from a provider-confirmed failed text or template message, choosing an active sender number with current Meta authorization that passes fresh consent, routing, team, and service-window/template checks. The retry is a new message in the shared history; an existing retry claim prevents duplicate clicks. Media is not replayed from the archive and must be attached and scanned again. Unknown, pending, and HTTP 5xx outcomes remain held for reconciliation.

If a send-status callback arrives before the API response stores Meta's message ID, the webhook processor correlates it only when sender number, recipient phone, timestamp window, and a single pending/uncertain outbound message agree. Ambiguous matches remain queued for webhook recovery instead of being guessed. Scheduled or administrator-triggered webhook recovery moves retry claims that remain in `PROCESSING` after five minutes to `NEEDS_REVIEW`; it does not automatically resend them.

Admin → Webhook health diagnostics show unresolved retry claims by status and timestamp without including customer content or phone numbers. A stale retry appears as requiring review; reconcile its provider status before sending again.

## Saved replies

Owners and admins can create, edit, deactivate and reorder saved replies from Admin → Saved replies. Each reply can have a unique shortcut; agents can open the composer picker or type `;shortcut` followed by Space or Tab to insert it. Reply bodies support `{{customer_name}}` and `{{agent_name}}`. Saved replies are workspace-scoped in PostgreSQL and their configuration changes are audited. Apply the latest migration with `npm run db:migrate` before using this feature; it is unavailable in local JSON mode.

Agents can save and restore named inbox filter combinations from the filter panel. With PostgreSQL configured, these personal views are stored per user and workspace so they follow that user across devices; existing browser-stored views are imported on first load. Local JSON development mode keeps views in browser storage. Views include search, assignment tab, status, number, team, tag and date filters.

## Current foundation

- WhatsApp-style shared inbox with search and unread state
- Channel-specific conversation view with a collapsible customer-wide timeline, thread switching, per-thread status and assignment, sender-change notices with a draft team-only follow-up reminder, and the selected number’s WhatsApp service-window status
- Customer directory with persistent local contact creation, audited email/source/owner/tag/custom-field editing, and retained phone identifiers
- Admin duplicate suggestions and audited contact merges that preserve message IDs and keep a source-ID merge record
- Owner/admin customer export as JSON or a ZIP with available clean attachments, linked conversation history and associated audit events
- Administrator-only audited exports, legal-hold placement/release, and permanent customer deletion that scrubs matching stored webhook payloads
- One-time, email-verified team invitations with self-set passwords, audited role changes, team assignment, team routing, and Mine / Unassigned / specific-team inbox filters
- Account security page with password change, active-session listing, individual revocation, and revoke-other-sessions control
- Forgot-password flow with generic response, rate limiting, one-time expiring links, and session revocation on recovery
- Authenticator MFA enrollment/challenge, encrypted TOTP seeds, one-time recovery codes, and admin change guards
- Persistent in-app administrator alerts for disconnected numbers, account restrictions, quality warnings, webhook retry exhaustion, token authorization failures, and failover events
- PostgreSQL-backed login throttling, hashed credential/IP keys, and immediate session invalidation after account-role changes
- Internal team-only notes and editable conversation tags
- Admin-managed canned replies with shortcuts and customer/agent name personalization
- Personal saved inbox views for common search and filter combinations
- Contact-level WhatsApp consent status, evidence source, wording version, actor and timestamp history; manual consent changes require both evidence and wording version, and unconsented and opted-out replies are blocked in the composer and message API
- Sender-number selector backed by configured numbers, with administrator-managed priority ordering and per-team number access enforced by the send APIs
- Responsive desktop-first application shell
- shadcn/ui configuration and shared Button, Badge, Avatar, Input, Textarea, Separator, Dialog, Message, Bubble, Marker, and MessageScroller primitives used throughout the inbox
- PRD requirements for admin authentication, roles, number management, and guarded failover

The PostgreSQL adapter stores messages under the sender-number conversation while presenting one combined customer history in the inbox. Agents can manually reroute future messages to another eligible, approved active number from the conversation details to a currently authorized sender number; a confirmation explains the customer-facing number and separate WhatsApp thread boundary. The reroute preserves existing history, creates or reopens the destination-number thread, and records an audit event. Internal notes and consent evidence are stored separately from customer-visible messages.

Reports includes a 30-day first-response median and 95th percentile, the unanswered queue count/age buckets, webhook backlog and oldest-event age, outbound failure rate for the last 24 hours, active sender-number states, and recent failover events. Inbox conversations with persisted inbound timestamps and no successful reply show their oldest unanswered age; resolved conversations are excluded. Only persisted successful agent replies count as a response. Operational metrics require PostgreSQL; local demo mode explains the requirement instead of displaying fabricated numbers.

Admin → Audit history provides workspace-scoped search, target filtering, and pagination for recorded administrative and customer-data events, including actor, target, timestamp, and available request context. Before/after values and event details are expandable and common secret-bearing keys are redacted. This view requires PostgreSQL and an Owner/Admin session.

## Next steps for a connected deployment

1. Configure PostgreSQL and `SESSION_SECRET`, then apply the checked-in migrations with `npm run db:migrate`.
2. Configure a verified Resend sender, `APP_BASE_URL`, and the password-reset environment variables.
3. Enroll MFA on every owner/admin account and complete an operational security review before exposing admin access publicly.
4. Configure Meta Facebook Login for Business / Embedded Signup, complete the applicable App Review and business permissions, and connect business-owned assets from Admin → WhatsApp numbers. Review imported numbers, confirm each Meta asset check passes, approve them for local routing, and then verify webhook delivery and a test send before production traffic.
5. Create teams and assign customers from the inbox. Define team and country-prefix rules from Admin → Routing. Edit customer profiles to maintain email, source, owner, tags and JSON custom fields; changing a primary phone retains both numbers as contact identifiers. A matching rule is authoritative: if its listed numbers are no longer active, the CRM holds the new conversation instead of falling through to a broader rule.
6. Configure a scheduled authenticated `POST /api/admin/webhooks` using `WEBHOOK_RECOVERY_SECRET` to recover pending events and media archives; administrators can also trigger recovery from Admin → Webhook health.
7. Verify approved template sync and dispatch against a Meta test WABA, including status changes and each supported variable shape.
8. Verify guarded failover and optional number-change notices against a Meta test WABA before enabling them for live traffic. The current implementation recognizes only error code `133010`; confirm its sender-number scope against the actual Meta response in your deployment before enabling automatic switching in production. Do not add error codes without confirming they identify a sender-number problem.

When configured with a business-owned Cloud API token, PostgreSQL, and onboarded phone-number IDs, the app can send text messages, approved templates and supported media; receive signed inbound/status webhooks; archive attachments encrypted in PostgreSQL; and optionally retry once on an administrator-approved active number in the same WABA for the configured sender-number error. Admins can create country-prefix and team routing rules, maintain persistent teams and memberships, change team roles, deactivate/reactivate accounts, and configure an optional Utility-template transition notice. The app is not a production-complete WhatsApp client: PostgreSQL-backed approval and reactivation require an authenticated Meta asset-list check, but that check does not verify webhook delivery, account health, or live message acceptance. Live malware-scanner configuration, provider/live database verification, and a production security review remain outstanding. Complete managed secret storage, MFA enrollment for every administrator, number onboarding, scheduler setup, and live failover/notice verification before production rollout.
